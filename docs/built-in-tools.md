# Built-in local tools

llamafile inherits a set of local tools from `llama-server`, llama.cpp's HTTP
server component. These tools let a model inspect files, search their contents,
edit files, run commands, and read the current time from the machine running
llamafile.

The tools are intended for the bundled Web UI. The Web UI runs the agent loop:
it sends the enabled tool definitions to the model, asks for permission before
executing a requested tool, calls the server-side implementation, and sends the
result back to the model. The regular chat completion API does not execute
arbitrary tool calls automatically.

> [!WARNING]
> Built-in tools act with the operating-system permissions of the llamafile
> process. Some can read or change local files or execute arbitrary commands.
> They are disabled by default. Enable only the tools you need and do not expose
> a tool-enabled server to an untrusted network.

## Enable built-in tools

Pass `--tools` in server mode. Use `all` to enable every built-in tool, or a
comma-separated list to enable selected tools:

```sh
# Enable every built-in tool
llamafile -m model.gguf --server --tools all

# Enable a read-only subset
llamafile -m model.gguf --server \
  --tools read_file,file_glob_search,grep_search,get_datetime
```

For a model-bundled llamafile, use its filename in place of `llamafile -m
model.gguf`:

```sh
./ModelName.llamafile --server --tools read_file,grep_search
```

Open the Web UI at <http://localhost:8080/> after the model loads. A model needs
a tool-capable chat template to request tools reliably. Do not start the server
with `--no-jinja`; on builds where Jinja is not already enabled by default, add
`--jinja`.

`--agent` enables all built-in tools and the experimental MCP proxy. Prefer
`--tools` when you only need local tools, because it enables a smaller surface.

The tool set comes from the bundled llama.cpp version and can change between
llamafile releases. Run the following command for the authoritative list in a
particular executable:

```sh
llamafile --server --help
```

## How tool use works

For each tool request, the Web UI:

1. Receives the tool name and arguments generated by the model.
2. Shows a permission request. The user can deny the call or allow it.
3. Asks the llamafile server to execute the tool.
4. Adds the result to the conversation as a tool message.
5. Lets the model continue with the new information.

This loop runs in the browser. Closing the Web UI stops its participation in
the loop, although it does not stop the llamafile server.

## Available tools

| Tool | Access | Purpose |
| --- | --- | --- |
| `read_file` | Read | Read all or part of a file. |
| `file_glob_search` | Read | Find files whose paths match a glob. |
| `grep_search` | Read | Search files for matching text. |
| `exec_shell_command` | Execute | Run a host shell command. |
| `write_file` | Write | Create or replace a file. |
| `edit_file` | Write | Replace selected text in an existing file. |
| `get_datetime` | Read | Get the server's current date and time. |
| `get_info` | Read | Get the runtime operating system and working directory. |

### `read_file`

Reads a text file, optionally limited to a 1-based inclusive line range.

| Parameter | Required | Description |
| --- | --- | --- |
| `path` | Yes | Path to the file. Relative paths are resolved from the llamafile process's working directory. |
| `start_line` | No | First line to return. Defaults to `1`. |
| `end_line` | No | Last line to return, inclusive. Defaults to the end of the file. |
| `append_loc` | No | Prefix each returned line with its line number. Defaults to `false`. |

The maximum response is 16 KiB. Reading a file larger than 16 KiB without
`end_line` returns an error; use `start_line` and `end_line` to read it in
parts. A selected range is truncated if its output exceeds 16 KiB.

### `file_glob_search`

Recursively lists files beneath a directory that match a glob pattern.

| Parameter | Required | Description |
| --- | --- | --- |
| `path` | Yes | Base directory to search. |
| `include` | No | Include glob. Defaults to `**`. |
| `exclude` | No | Glob of paths to exclude. |

A pattern without `/`, such as `*.cpp`, matches a filename at any depth. A
pattern containing `/` matches the relative path and is treated as though it
started with `**/` unless it is already anchored.

Inside a Git repository, the tool uses Git's file list so files excluded by
`.gitignore` are skipped. Otherwise it walks the directory and skips common
generated directories such as `.git`, `node_modules`, `build`, `dist`, and
`target`. It returns at most 100 paths and reports the total number of matches.

### `grep_search`

Searches a file or directory for matching lines.

| Parameter | Required | Description |
| --- | --- | --- |
| `path` | Yes | File or directory to search. |
| `pattern` | Yes | ECMAScript regular expression, or literal text when `literal` is `true`. |
| `include` | No | Include glob used when `path` is a directory. Defaults to `**`. |
| `exclude` | No | Glob of paths to exclude. |
| `return_line_numbers` | No | Include line numbers. Defaults to `false`. |
| `literal` | No | Treat `pattern` as literal text. Defaults to `false`. |
| `ignore_case` | No | Perform a case-insensitive search. Defaults to `false`. |
| `context_lines` | No | Include this many lines before and after each match. Defaults to `0`. |

Directory searches follow the same Git-ignore, generated-directory, and glob
rules as `file_glob_search`. The result is limited to 100 matches. Context
lines do not count as additional matches.

### `exec_shell_command`

Runs a command through `sh -c` on Unix-like systems or `cmd /c` on Windows.
Standard output and standard error are combined.

| Parameter | Required | Description |
| --- | --- | --- |
| `command` | Yes | Shell command to execute. |
| `timeout` | No | Timeout in seconds. Defaults to `10` and is capped at `60`. |
| `max_output_size` | No | Maximum captured bytes. Defaults to and is capped at 16 KiB. |

The result includes the process exit code and reports when a timeout terminated
the command. This is currently the only built-in tool whose output streams live
in the Web UI.

> [!CAUTION]
> This tool can run any command available to the llamafile process. Shell
> syntax, redirections, pipelines, and environment expansion are interpreted by
> the host shell.

### `write_file`

Creates or completely replaces a file. Missing parent directories are created
when possible.

| Parameter | Required | Description |
| --- | --- | --- |
| `path` | Yes | File to create or replace. |
| `content` | Yes | Complete new contents of the file. |

Use `edit_file` when only part of an existing file should change.

### `edit_file`

Applies one or more text replacements to an existing file.

| Parameter | Required | Description |
| --- | --- | --- |
| `path` | Yes | File to edit. |
| `edits` | Yes | Non-empty array of replacement objects. |
| `edits[].old_text` | Yes | Existing, non-empty text that identifies one unique region of the file. |
| `edits[].new_text` | Yes | Replacement text. |

Every `old_text` value is matched against the original file, not against the
result of an earlier replacement in the same call. Matches must be unique and
must not overlap. The tool rejects a call that makes no change. It can tolerate
some differences in trailing whitespace, typographic quotes, dashes, and space
characters when an exact match is not found, but callers should provide exact
text whenever possible.

### `get_datetime`

Returns the current date and time in UTC.

| Parameter | Required | Description |
| --- | --- | --- |
| `format` | No | `strftime`-style output format. Defaults to `%Y-%m-%dT%H:%M:%SZ`. |

### `get_info`

Returns the runtime operating-system name and version and the current working
directory. It accepts no model-supplied arguments.

## Security and sandbox behavior

Unless `--cors-origins` is set explicitly, enabling built-in tools changes the
allowed browser origin from `*` to localhost. This CORS setting limits browser
requests; it is not authentication and does not protect a server that is
reachable by other clients. Keep the default loopback bind address when
possible, and configure `--api-key` before exposing a server on another
interface.

The Web UI permission prompt is also not a server-side security boundary. Once
tools are enabled, a client that can reach the internal tool endpoint and
satisfy any configured API key can invoke an enabled tool without using the Web
UI. Select the smallest useful tool list at startup.

llamafile's sandbox changes which tools can succeed:

| Runtime mode | Effect on built-in tools |
| --- | --- |
| CPU-only `--server` on Linux or OpenBSD | The default sandbox permits reads but blocks file writes, process creation, and command execution. `write_file`, `edit_file`, and `exec_shell_command` therefore fail. |
| CPU-only `--server --confine-reads` | The same restrictions apply, and reads are limited to the executable and configured model, adapter, media, and static-file directories. Arbitrary project paths may be invisible. |
| GPU server | The sandbox is skipped because GPU drivers require system access that the sandbox cannot allow. Enabled tools run with the process's normal permissions. |
| Default combined TUI and server mode | The sandbox is skipped because the in-process TUI needs an HTTP client connection. |
| `--unsecure` or an operating system without supported sandboxing | The sandbox is disabled or unavailable; enabled tools run with the process's normal permissions. |

Enabling tools in an otherwise sandboxed server relaxes the network restriction
so the server can make outbound connections, but it does not add permission to
write files or execute programs. See [Security](security.md) for the complete
sandbox model.

## Use tools from compatible APIs

The OpenAI-compatible Chat Completions and Responses APIs and the
Anthropic-compatible Messages API can ask a model to call tools. They do not
execute built-in tools automatically. The client must approve each request,
invoke `POST /tools` or its own implementation, return the result in the
selected API's tool-result format, and continue the conversation.

See [API server: Tool calling](api.md#tool-calling) for the complete agent
loop, tool-definition mappings, and OpenAI- and Anthropic-style examples.

## Internal `/tools` API

The bundled Web UI discovers and invokes tools through `GET /tools` and `POST
/tools`. These are HTTP endpoints, so command-line clients such as `curl` can
call them directly.

> [!IMPORTANT]
> `/tools` is an experimental internal interface between the Web UI and
> `llama-server`. It can change or be removed without notice. Do not depend on
> it as a stable downstream application API. Applications should normally use
> the model's [function-calling API](api.md#tool-calling), execute approved
> tools in the application, and return the results to the model as tool
> messages.

The examples below assume the default address, `http://127.0.0.1:8080`. If the
server was started with an API prefix, such as `--api-prefix /llama`, prepend
that prefix: `/llama/tools`.

The endpoint is available when at least one built-in or MCP tool is configured.
If tools are disabled, both methods return HTTP `403`. When `--api-key` or
`--api-key-file` is configured, authenticate in either of these forms:

```sh
-H 'Authorization: Bearer YOUR_API_KEY'
```

```sh
-H 'X-Api-Key: YOUR_API_KEY'
```

Omit the authentication header when the server has no API key. A direct
`POST /tools` call executes immediately: the server does not reproduce the Web
UI's permission prompt.

### List tools with `GET /tools`

```sh
curl http://127.0.0.1:8080/tools
```

The response is a JSON array containing every enabled built-in tool and any
tools exposed by configured MCP servers. For example, an enabled `get_info`
tool is described as follows:

```json
[
  {
    "display_name": "Get Runtime Info",
    "tool": "get_info",
    "type": "builtin",
    "permissions": {
      "write": false
    },
    "uses_cwd": true,
    "definition": {
      "type": "function",
      "function": {
        "name": "get_info",
        "description": "Returns runtime info: the OS name/version and the current working directory",
        "parameters": {
          "type": "object",
          "properties": {}
        }
      }
    }
  }
]
```

| Field | Description |
| --- | --- |
| `tool` | Identifier to send in a `POST /tools` request. |
| `display_name` | Human-readable label for the UI. |
| `type` | `builtin` for a server tool or `mcp` for a tool exposed by an MCP server. |
| `permissions.write` | UI hint that the tool can change state. It is not server-side authorization. |
| `uses_cwd` | Whether the built-in tool uses a working-directory context. |
| `definition` | OpenAI-compatible function definition supplied to the model. |

MCP tool identifiers have the form `<server-name>_<tool-name>`. If that name
collides with another exposed tool, the later MCP tool is omitted.

### Invoke a tool with `POST /tools`

Send a JSON request with `Content-Type: application/json`:

| Field | Required | Description |
| --- | --- | --- |
| `tool` | Yes | Tool identifier returned by `GET /tools`. |
| `params` | No | Object containing the tool arguments. Defaults to `{}`. |
| `stream` | No | Stream supported tool output with server-sent events. Defaults to `false`. |

For example, this reads the first 20 lines of `README.md`:

```sh
curl http://127.0.0.1:8080/tools \
  -H 'Content-Type: application/json' \
  -d '{
    "tool": "read_file",
    "params": {
      "path": "README.md",
      "start_line": 1,
      "end_line": 20
    }
  }'
```

A text-producing tool returns its text in `plain_text_response`:

```json
{
  "plain_text_response": "# llamafile\n..."
}
```

When continuing an agent loop, use that string directly as the tool message's
`content`:

```json
{
  "role": "tool",
  "content": "# llamafile\n..."
}
```

Other successful results and tool-level errors are ordinary JSON objects. For
example:

```json
{
  "error": "cannot stat file: missing.txt"
}
```

Serialize the complete object when placing one of these results in a tool
message's string `content`. MCP text content is combined into a
`plain_text_response`; MCP RPC and tool errors are returned in `error`.

### Execution-context headers

The caller, rather than the model, can set execution context with headers. If a
request body contains `cwd`, `runtime`, or `resp_type` parameters, the server
removes them before applying the corresponding header value.

| Header | Description |
| --- | --- |
| `x-tool-cwd` | Working directory for tools whose `uses_cwd` field is `true`. Relative paths and commands are resolved there. |
| `x-tool-runtime` | Run the built-in tool in an existing isolate instead of on the host. Accepted forms are `docker-container:<id>`, `podman-container:<id>`, and `ssh:<target>`. This overrides `--tools-runtime` for the request. |
| `x-resp-type: base64` | Make `read_file` return `{ "base64": "...", "size_bytes": N }`. The base64 mode accepts files up to 32 MiB. |

For example:

```sh
curl http://127.0.0.1:8080/tools \
  -H 'Content-Type: application/json' \
  -H 'x-tool-cwd: /path/to/project' \
  -d '{"tool":"get_info","params":{}}'
```

Treat these as trusted runtime controls. In particular, do not let model output
choose an SSH target, container, or host working directory.

### Stream tool output

Set `stream` to `true` to receive server-sent events (SSE). Currently,
`exec_shell_command` is the only built-in tool that supports streaming:

```sh
curl -N http://127.0.0.1:8080/tools \
  -H 'Content-Type: application/json' \
  -d '{
    "tool": "exec_shell_command",
    "params": {"command": "echo hello"},
    "stream": true
  }'
```

Each output event contains a chunk:

```text
data: {"chunk":"hello\n"}
```

The last event reports completion:

```text
data: {"done":true}
```

If invocation throws an exception, the last event is instead:

```text
data: {"done":true,"error":"..."}
```

The stream closes after the `done` event. Unlike the chat completions stream,
there is no `[DONE]` sentinel. Requesting streaming for a tool that does not
support it returns HTTP `404`.

### HTTP status codes

| Status | Meaning |
| --- | --- |
| `200` | The list or invocation was handled. Check the response body for a tool-level `error`. |
| `400` | The request body is invalid JSON or has the wrong JSON shape or types. |
| `401` | An API key is required and is missing or invalid. |
| `403` | No built-in or MCP tools are enabled. |
| `404` | The tool name is unknown, or `stream: true` was requested for a non-streaming tool. |
| `500` | An unexpected server-side exception occurred. |

## Troubleshooting

### No tools appear in the Web UI

Confirm that the server was started with `--tools`, then reload the Web UI. Run
`llamafile --server --help` to check that the tool name exists in that release.

### The model describes a tool call instead of requesting it

Make sure Jinja is enabled and use a model with a tool-aware chat template. If
necessary, select a compatible template with `--chat-template` or
`--chat-template-file`.

### A write or command returns permission denied

Check whether the CPU server sandbox is active. This is expected for
`write_file`, `edit_file`, and `exec_shell_command` in the default sandboxed
`--server` mode. Review the security tradeoffs before using `--unsecure`.

### A read or search cannot see a path

If `--confine-reads` is active, only the directories allowed at server startup
are visible. Without read confinement, normal filesystem ownership and
permissions still apply.
